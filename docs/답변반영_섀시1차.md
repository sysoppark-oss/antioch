## 1. 규칙 R1~R11

| 항목 | 판정 | 내용 |
|---|---|---|
| R1 서로게이트 쌍 절단 | 이미 있음 | 1차 구현부터 코드 포인트 단위로 자른다(`Array.from`). 시험도 있었다. |
| R1 비정상 수 | 수용 | 수치는 유한하고 절댓값 1e15 이하만 받는다. 넘으면 그 칸(추이선은 그 점)을 버린다. |
| R1 깊은 중첩·바이트 상한 | 미룸(2단계) | 전송 계층의 일이다. 한 줄 상한은 6.1 확정값(1MB)이 있으므로 64KB 로 바꾸려면 규격 변경 제안이 필요하다 — 2단계에서 "응답 한 줄 상한"과 중첩 깊이 상한을 함께 정한다. |
| R2 제거 문자 범위 | 수용 | C1(U+0080~009F), U+061C, U+200B~200F, U+2028·2029, U+FEFF 를 더했다. 이름표(제목·보조·단위)는 줄바꿈도 없애 한 줄로 만든다. |
| R2 겹친 결합 부호 | 수용 | 연속 결합 부호는 둘까지만 남긴다. |
| R2 암묵적 RTL | 수용 | 모듈 글자가 들어가는 칸마다 `unicode-bidi: isolate`, 넘침 자르기, 대시보드 영역 `contain: content`. |
| R3 가짜 파이프로 30초 묶기 | 수용 | 공개된 파이프 이름이 바뀌면 30초 대기를 풀고 다시 본다. 단 시도 간격은 2초 이상(값을 계속 바꿔 대는 프로그램에 끌려다니지 않게). 화면에 "확인 실패 — 비정상 파이프일 수 있습니다". |
| R4 HKCU 가 HKLM 슬롯 선점 | 반박 | 전제가 설계와 다르다. 슬롯 **등록**은 HKLM 뿐이다(5.1, 8.3). HKCU 에는 이미 HKLM 에 등록된 앱형 모듈의 "실행 중 파이프 이름"만 온다. HKCU 만으로는 슬롯이 생기지 않는다. → 2단계 발견 코드에 "HKLM 에 없는 id 의 HKCU 값은 무시"를 시험으로 고정한다. |
| R5 미래 시각으로 상단 점유 | 수용 | 순서와 보관을 모듈이 적은 시각이 아니라 **받은 순서**로 바꿨다. |
| R6 느슨한 시각 범위 | 수용 | 지금보다 60초 넘게 앞서거나 30일 넘게 지난 시각은 받은 시각으로 고쳐 적고 "보정" 표시를 붙인다. 원래 값은 `rawTs` 에 남긴다. |
| R7 가벼운 사건으로 치명 사건 밀어내기 | 부분 수용 | 초당 10건 가운데 info·notice 는 5건까지만 쓴다(나머지는 warn·critical 몫). 같은 종류 사건 합치기는 넣지 않았다 — 합치는 기준을 섀시가 정하면 모듈의 사건을 섀시가 해석하게 된다. 묶기는 6.1 대로 모듈의 일이다. |
| R8 규칙 안에서 바쁘게 만들기 | 부분 수용 | 위젯이 10개 이상인 모듈은 새로 고침을 15초 이상으로 늦춘다. "가운데 패널만 자주"는 미룸(3단계, 실제 부하를 잰 뒤). |
| R9 붙었다 끊기 되풀이 | 수용 | 다시 붙기를 0 → 2초 → 4초 … 최대 60초로 늦추고, 세 번째부터 "연결이 불안정합니다"를 보인다. 1분 넘게 붙어 있었으면 처음으로 되돌린다. |
| R10 권한 값 변형 | 이미 있음 | 소문자 정확 일치만 통과한다(시험 있음). |
| R10 조작 이름 피싱 | 수용 | 조작 이름 24자, 섀시가 "읽기 전용 · 여기서는 누를 수 없음" 표시를 고정으로 붙인다. |
| R11 말씀 파일 변조 | 이미 있음 / 반박 | 전제가 구현과 다르다. 말씀 자료는 실행 중에 파일로 읽지 않고 빌드 때 프로그램 안에 넣는다. 본문 상한도 있다(2,000자, 가장 긴 구절이 그 안인지 시험으로 확인). 설치 폴더 ACL 점검은 제미나이 3-A 수용 항목으로 설치 단계에 들어간다. |

## 2. 질문 Q1~Q7

| 항목 | 판정 | 내용 |
|---|---|---|
| Q1 상태등 흉내 그림 글자 | 수용 | 이름표에서 그림 글자(Extended_Pictographic)를 뺀다. |
| Q1 동형이의 문자(라틴·키릴 섞기) | 미룸 | 섞인 문자 검사는 오탐이 많다(한글 + 라틴은 정상). 대신 Q2 의 "출처는 섀시가 따로 붙인다"로 막는다. 필요하면 UTS #39 의 섞임 검사를 뒤에 더한다. |
| Q1 추이선 극단값·모두 같은 값 | 수용 / 이미 있음 | 극단값은 R1 의 수 상한으로 막는다. 모두 같은 값은 1차부터 처리돼 있었고 시험을 더했다. |
| Q2 남의 이름 흉내 | 수용 | 표시 이름이 같은 모듈이 둘이면 뒤쪽에 `(슬롯 id)`를 붙인다. 통합 피드의 출처는 섀시가 붙이는 별도 칸으로 떼어 모듈이 쓴 제목과 섞이지 않게 했다. "HKCU 모듈" 구분은 R4 와 같은 까닭으로 해당 없음. |
| Q3 한 모듈의 보관함 독점 | 수용(방식 변경) | 넘칠 때 "가장 많이 가진 모듈의 가장 옛것"부터 버린다. 모듈별 고정 몫(30건)보다 단순하고, 모듈이 몇 개든 한 모듈이 남을 밀어내지 못한다. |
| Q4-1 hello 대기 중 등록 삭제 | 이미 있음 | 발견과 연결이 한 바퀴 안에서 차례로 돌아 그 사이에 등록부를 다시 읽지 않고, 다음 바퀴에서 사라진 슬롯은 연결을 닫고 뺀다. 늦은 콜백은 세대 번호로 버린다. |
| Q4-2 응답 시한 | 수용 | hello·describe·subscribe 3초, health·widgets 5초. 넘으면 끊고 "응답이 늦어 연결을 끊었습니다". |
| Q4-3 다시 켜진 모듈의 번호 겹침 | 수용(방식 변경) | "id·시각·제목이 모두 같은 것"만 되풀이로 보고 버린다. id 만 같고 내용이 다르면 새 사건이다. 실행 세대를 id 에 넣는 것은 모듈 쪽 규격이라 변경 제안 후보로 남긴다. |
| Q5 HKCU 를 계속 덮어쓰는 공격 | 부분 수용 | 섀시 쪽: R3 반영분. 규격 쪽: 서비스형 모듈(스토리방화벽)은 **이미** 파이프 이름을 HKLM 에 올린다(5.1). 남는 것은 앱형 모듈(NetX)의 HKCU 값이며, 같은 사용자 권한의 프로그램이 계속 덮어쓰면 막을 수 없다 — 8.3 "못 막는 것"과 같은 선이다. 화면에 까닭을 보이는 것까지가 섀시의 몫이다. |
| Q6 말씀 언어 값 | 미룸(3단계) | 등록부를 읽는 코드가 생길 때 `RegGetValueW` 에 `RRF_RT_REG_SZ` 와 길이 상한을 걸고, 맞지 않으면 다음 순서로 넘어간다. 기본값은 `ko` 고정이 아니라 확정 순서(HKCU → HKLM → Windows 표시 언어 → en → ko)다. |
| Q7 `state` 이름 겹침 | 변경 제안 | 3장 P1. |

## 3. 제안 P1~P4

| 항목 | 판정 | 내용 |
|---|---|---|
| P1 위젯 색조 칸 이름을 `tone` 으로 | **기획자 결정 필요** | 지적이 맞다. 다만 6.5 초안의 예시가 `state` 이고 이 저장소의 고정 예시는 그 글자 그대로다. 공통 규격은 저장소에서 먼저 바꾸지 않으므로 변경 제안으로 올린다. 지금 구현은 위젯의 `state` 에 health 값(degraded·down)이 오면 "색조 없음"으로 두고 ok 로 바꾸지 않는다. |
| P2 `widget_schema_version` | 반박 | 판 구분은 `rack.hello` 의 `api`(메이저·마이너)가 이미 한다. 판 표시를 둘로 두면 어긋날 자리가 하나 더 생긴다. 자료 모양이 확정될 때 마이너를 올린다. |
| P3 R3·R8 을 규격에 넣기 | 변경 제안 | 6장에 "응답·사건의 모듈 이름은 접속한 슬롯과 같아야 한다", "rack.widgets 는 요청받은 id 만 돌려준다"를 넣자는 제안으로 올린다. |
| P4 그림을 보내는 길 금지 유지 | 수용 | 그대로 둔다. 이야기 그래프가 필요해지면 노드 50·선 100 상한의 자료 전용 위젯 종류를 변경 제안으로 올린다. |

## 4. 답변에는 없었지만 반영하다 찾은 것

- 1차 커밋의 `validate.ts` 정규식에 글자 방향 전환 문자가 **이스케이프가 아니라 글자 그대로** 들어가 있었다(작성 도구가 `\u202e` 표기를 실제 글자로 바꿈). 동작은 같았지만 소스를 읽는 사람의 화면을 뒤집을 수 있는 글자다. 이스케이프 표기로 되돌렸다.

## 5. 남은 것
