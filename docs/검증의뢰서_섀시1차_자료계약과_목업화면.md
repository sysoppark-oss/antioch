## 1. 이번에 만든 것

1. **자료 계약을 두 언어로 고정.** Rust `crates/epistle`(타입 + 검사)와 TypeScript `app/src/epistle`(타입 + 걸러 내기). 설계 문서 6.3~6.6, 11.7 의 예시를 `fixtures/*.json` 에 글자 그대로 두고 **두 쪽 시험이 같은 파일을 읽는다**(Rust 9건, 화면 38건 통과).
2. **섀시 상태 관리(`app/src/core/chassis.ts`).** 발견 → `rack.hello` → `rack.describe` → `rack.health`·`rack.widgets` → `rack.subscribe`. 화면(DOM)을 모르는 순수 로직이다.
3. **홀로그램 콘솔 화면.** 기획자 승인 맛보기의 3D 코버플로우를 옮겨, 패널 내용을 위젯 자료에서 만든다. 지금은 로컬 목업 피드에 붙어 있다(3단계에서 실클라이언트로 교체).
4. **오늘의 말씀 내장 슬롯.** 자료 묶음(`word/`)을 그대로 읽고, README 확인 값 7개를 시험으로 고정.

## 2. 섀시가 모듈 자료를 다루는 규칙 (구현된 그대로)

| # | 규칙 |
|---|---|
| R1 | 모듈에서 온 값은 전부 `unknown` 으로 받아 걸러 낸 뒤에만 쓴다. 필수 칸의 형식이 틀리면 그 항목을 버리고, 길이는 자른다(제목 80자, 보조 200자, 목록 50건, 추이선 240점, 위젯 24칸). 모르는 칸·모르는 위젯 종류는 무시한다. |
| R2 | 화면에는 `textContent` 로만 넣는다. `innerHTML` 을 쓰지 않는다. 제어 문자와 글자 방향 전환 문자(U+202A~202E, U+2066~2069)는 뺀다. 페이지 CSP 는 `default-src 'self'`. |
| R3 | **이름 대조:** `rack.hello` 응답의 `module`, 매니페스트의 `id`, 사건의 `module` 이 모두 그 연결의 **등록부 슬롯 id** 와 같아야 한다. 다르면 hello·describe 는 슬롯을 "확인 실패"로 두고 30초 뒤에야 다시 보며, 사건은 버린다. |
| R4 | 슬롯 id 는 `[a-z0-9_]{1,32}`. 형식 위반, 중복 등록, 내장 슬롯(`word`)과 같은 이름의 등록은 받지 않는다. |
| R5 | 사건 id 는 `<슬롯 id>:evt:<[A-Za-z0-9_.-]{1,64}>`. 같은 id 는 한 번만 보관한다. 최근 200건, 시각 내림차순. |
| R6 | 시각은 epoch **초**(정수, 0 초과 2100년 미만). 밀리초·문자열·소수는 버린다. |
| R7 | 사건은 모듈당 초당 10건까지 받고 넘는 것은 버린다(버린 수를 패널에 표시). |
| R8 | 위젯 응답에서 **요청한 id** 가 아닌 칸과 중복 id 는 버린다. 새로 고침 주기는 5초~1시간으로 가둔다. |
| R9 | 연결이 끊기면 그 슬롯의 상태·위젯을 **비우고** "연결 끊김"으로 둔다(옛 수치를 지금 값처럼 보이지 않게). 다시 붙으면 hello 부터 전부 다시 받는다. 옛 연결에서 늦게 온 콜백은 연결 세대 번호로 버린다. |
| R10 | 권한: 모르는 `granted` 값은 버린다. 이 단계의 섀시는 읽기만 한다. 매니페스트의 `actions` 는 누를 수 없는 표시로만 그린다. |
| R11 | 말씀은 `rack.event` 를 내지 않고(11.2), 본문을 자르지 않으며, 글자에 상태 색·투명도를 쓰지 않는다. |

## 3. 설계 문서에 없어 이 저장소가 정한 것 (제안 — 판단을 부탁합니다)

- **P1. 위젯의 색조 값.** 6.5 예시의 `"state": "caution" | "danger"` 를 `ok | caution | danger | off` 네 값으로 정했다. `rack.health` 의 `state`(ok·degraded·down·starting)와 이름은 같고 값 집합이 다르다.
- **P2. `status`·`spark`·`timeline` 의 자료 모양.** `fixtures/widgets_proposed.json`.
- **P3. 이름 대조(R3)와 요청하지 않은 위젯 버리기(R8).** 설계 문서에는 명시가 없다.
- **P4. 승인 맛보기에 있던 "이야기 그래프"·"경로 레이더" 그림은 6개 위젯 종류로 표현할 수 없어 뺐다.** 모듈이 그림(HTML·SVG)을 보내는 길은 열지 않는다는 원칙 때문이다. 대신 `spark` 로 추이를 그린다. 필요하면 "노드·선 자료만 받는 위젯 종류"를 변경 제안으로 올릴 수 있다.

## 4. 묻고 싶은 것 (깨지는 입력·순서 먼저)

**Q1. 걸러 내기(R1·R2)를 지나 화면을 속이는 입력이 있는가?** 예: 제목 80자 안에서 다른 모듈·섀시 자신의 문구처럼 보이게 하는 글자(동형이의 문자, 결합 문자, 폭 없는 문자, 이모지 상태등 흉내), `unit` 12자에 넣는 속임수, 매우 큰 수·지수 표기, `spark` 의 극단값(±1e308, 모두 같은 값)으로 그림이 깨지는 경우.

**Q2. 이름 대조(R3)로 막지 못하는 "남의 일처럼 보이게 하기"가 있는가?** 모듈 A 가 자기 사건의 `title` 에 "스토리방화벽 · 차단 해제됨" 같은 글을 넣으면 개요 패널의 통합 피드에서 `A의 제목 · title` 로 보인다. 모듈 `title` 자체를 "스토리방화벽"으로 등록하는 경우도 있다(슬롯 id 는 다르고 표시 이름만 같음). 섀시가 표시 이름 중복을 어떻게 다뤄야 하는가?

**Q3. 사건 보관(R5·R7)을 악용해 중요한 사건을 밀어내는 순서가 있는가?** 한 모듈이 초당 10건을 20초 내면 다른 모듈의 사건이 200건 밖으로 밀린다. 미래 시각(2099년)을 단 사건은 항상 맨 위에 남는다. 모듈별 몫 나누기, "지금보다 N초 넘게 앞선 시각은 받은 시각으로 고쳐 적기" 가운데 무엇이 맞는가? 고쳐 적으면 생기는 문제는?

**Q4. 끊김·재동기화(R9)가 깨지는 순서가 있는가?** hello 를 기다리는 사이 등록이 사라짐, describe 는 답하고 widgets 에서 멈춤(응답 없음 — 지금 구현에는 **응답 시한이 없다**. 2단계 전송 계층에 넣을 예정), 붙었다 끊기를 빠르게 되풀이, 다시 붙은 뒤 사건 id 를 처음부터 다시 세는 모듈(옛 사건과 id 가 겹쳐 새 사건이 버려짐).

**Q5. "확인 실패" 30초 재시도(R3)가 서비스 거부나 깜빡임 공격이 되는가?** HKCU 의 `Running\<id>` 를 고칠 수 있는 프로그램이 가짜 파이프 이름을 계속 써넣으면 그 슬롯은 계속 "확인 실패"로 보인다. 사용자에게 어떻게 보여야 하고, 진짜 모듈이 다시 붙을 길은 어떻게 보장해야 하는가?

**Q6. 내장 말씀 슬롯:** 말씀 언어를 3단계에서 HKCU → HKLM(`WordLang`) 순으로 읽는다. 값은 내장 목록(`ko`, `en`)과 글자 비교만 한다. 이 경로로 표시를 없애거나 다른 글을 보이게 할 수 있는가?

**Q7. P1~P4 의 제안 가운데 뒤에 가서 규격을 깨뜨릴 것이 있는가?** 특히 P1(같은 칸 이름 `state` 에 두 가지 값 집합).
