# 변경 제안 — 에피스틀 6장: 위젯 색조 칸 이름, 이름 대조, 사건 id (1판)

- 올린 곳: 안디옥 섀시 개발 세션, 2026-11-15
- 상태: **제안.** 올리는 것은 기획자 승인(2026-11-15), 내용의 확정은 아직이다. 확정 전에는 어느 프로그램도 이 문서를 근거로 구현하지 않는다.
- 대상: 「안디옥 플랫폼 설계와 에피스틀 규격 (0.19판 초안)」 6.2, 6.5, 6.6, 7장
- 나온 곳: 「답변반영 — 안디옥 섀시 1차」 3장 P1·P3, 2장 Q4-3 (제미나이 검증 답변 2026-11-14)
- 읽을 사람: `rack.widgets`·`rack.event` 를 내보내는 쪽(스토리방화벽, NetX)과 받는 쪽(섀시)

세 건 모두 **아직 어느 모듈도 `rack.widgets`·`rack.event` 를 내보내지 않는 지금** 정하면 고칠 코드가 섀시 저장소뿐이다. 스토리방화벽에 읽기 전용 `rack.*` 송출을 넣기(액션 플랜 2단계) 전에 정하는 것이 가장 싸다.

## 1. 위젯 색조 칸의 이름을 `state` 에서 `tone` 으로

### 지금
- `rack.health` 의 `state`: `ok | degraded | down | starting` (6.5)
- 위젯과 목록 항목의 `state`: 6.5 예시에 `"caution"`, `"danger"` 가 나온다. 값 목록은 문서에 없다.

같은 이름의 칸에 서로 다른 값 집합이 들어간다. 모듈 개발자가 위젯에 `"down"` 을 넣거나, 받는 쪽의 공용 코드가 둘을 섞어 다루면 위험 표시가 빠지거나 다른 색으로 보인다.

### 제안
- 위젯·목록 항목·시간순 항목의 색조 칸 이름을 **`tone`** 으로 한다. 값은 `ok | caution | danger | off` 네 가지.
- `rack.health` 와 `checks[]` 의 `state` 는 그대로 둔다.
- 받는 쪽은 모르는 `tone` 값을 "색조 없음"으로 그린다(`ok` 로 바꾸지 않는다).

```json
{"id": "blocked_today", "kind": "stat", "value": 37, "unit": "건", "trend": "up",
 "tone": "caution", "open": {"view": "blocked"}}
```

### 고칠 곳
설계 문서 6.5 의 예시 두 개와 7장 타입, 섀시 저장소의 `fixtures/widgets.json`·`crates/epistle`·`app/src/epistle`. 스토리방화벽·NetX 는 아직 내보내는 코드가 없어 고칠 것이 없다.

### 정할 것
(가) `tone` 으로 바꾼다 **[권고]** / (나) `state` 그대로 두고 값 목록만 문서에 적는다.

## 2. 이름 대조와 "요청한 위젯만"을 규격에 넣기

섀시는 지금 아래 두 가지를 지키지 않는 응답을 버린다. 규격에 적혀 있지 않으면 모듈을 만드는 쪽이 모르고 어겨 자료가 통째로 버려진다.

### 제안 — 6.2 아래에 "받는 쪽이 확인하는 것"으로 추가
1. **이름 대조.** `rack.hello` 응답의 `module`, `rack.describe` 의 `id`, `rack.event` 의 `module` 은 그 모듈이 등록부에 올린 슬롯 id(`HKLM\SOFTWARE\Antioch\Modules\<id>` 의 `<id>`)와 글자 그대로 같아야 한다. 받는 쪽은 hello·describe 가 다르면 연결을 끊고, 사건이 다르면 그 사건을 버린다. 모듈은 자기 이름으로만 말한다.
2. **슬롯 id 의 형식.** 영문 소문자·숫자·`_`, 1~32자.
3. **요청한 위젯만.** `rack.widgets` 의 `params.ids` 는 필수이고 24개 이하다. 응답에는 요청받은 id 의 위젯만, id 마다 한 번씩 싣는다. 받는 쪽은 요청하지 않은 칸과 중복을 버린다.
4. **표시 이름은 신원이 아니다.** 매니페스트의 `title` 은 글자로만 쓰인다. 통합 화면은 이름이 겹치는 모듈에 슬롯 id 를 붙여 보인다.

### 정할 것
(가) 네 줄을 6.2 에 넣는다 **[권고]** / (나) 섀시의 구현 규칙으로만 두고 규격에는 넣지 않는다.

## 3. 사건 id 는 다시 켜도 겹치지 않아야 한다

### 지금
6.6 예시는 `"id": "storyfirewall:evt:90211"` 이다. 모양(`<모듈>:evt:<값>`)의 규칙도, 값이 언제까지 유일해야 하는지도 문서에 없다. 모듈이 다시 켜질 때 번호를 1부터 다시 세면, 받는 쪽이 "이미 본 사건"으로 보고 새 사건을 버릴 수 있다.

### 제안 — 6.6 에 추가
1. 사건 id 는 `<슬롯 id>:evt:<값>`. `<값>` 은 영문·숫자·`_`·`.`·`-`, 1~64자.
2. `<값>` 은 **그 모듈이 다시 켜진 뒤에도** 앞서 쓴 값과 겹치지 않아야 한다. 저장소의 행 번호처럼 원래 겹치지 않는 값은 그대로 쓴다(스토리방화벽). 메모리에서 세는 번호라면 켜질 때마다 달라지는 값을 앞에 붙인다: `<시작 시각 epoch 초>-<번호>` (예: `netx:evt:1794355200-17`).
3. 받는 쪽은 id 만으로 되풀이를 판단하지 않는다. id·시각·제목이 모두 같은 것만 같은 사건으로 본다(규칙 2를 어긴 모듈의 새 사건을 잃지 않기 위한 안전판).
4. `ts` 는 epoch 초. 받는 쪽은 지금보다 60초 넘게 앞서거나 30일 넘게 지난 시각을 받은 시각으로 고쳐 적고 그 사실을 표시한다. 통합 사건 목록의 순서는 받은 순서다.

### 정할 것
(가) 네 줄을 6.6 에 넣는다 **[권고]** / (나) 1·2번만 넣고 3·4번은 섀시의 구현 규칙으로 둔다.

## 4. 확정되면 할 일
- 설계 문서 새 판에 반영(6.2, 6.5, 6.6, 7장).
- 섀시 저장소: 1번이 (가)면 `fixtures/widgets.json` 과 타입·걸러 내기·시험을 `tone` 으로 고친다. 2·3번은 이미 구현돼 있어 문서 근거만 바뀐다.
- 스토리방화벽·NetX: `rack.*` 송출을 만들 때 이 규칙으로 만든다. 지금 고칠 코드는 없다.
