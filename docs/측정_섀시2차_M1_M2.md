# 측정 — 안디옥 섀시 2차의 M1·M2 (2026-11-22)

- 무엇을: 「답변반영 — 안디옥 섀시 2차」 4장의 M1(띄운 뒤 경로 바꿔치기)과 M2(서버 핸들 물려주기)
- 어떻게: `crates/epistle/tests/win_measure.rs` — GitHub Windows 러너에서 실제 프로세스·폴더·파이프로 잰다. 판정하지 않고 적는 시험이다
- 어디서: 커밋 `1228538`, CI run-3. 원본 로그는 `ci-logs` 브랜치의 `epistle/run-3/<os>/test.log` (`M1|`, `M2|` 로 시작하는 줄)
- 잰 판: **Windows Server 2022 (10.0.20348.5870)**, **Windows Server 2025 (10.0.26100.33828)**. 실기기의 Windows 10·11 은 **재지 않았다**
- 러너의 시험 프로세스는 관리자 권한이다. 아래 동작들은 권한에 달린 것이 아니라고 보지만, 일반 권한에서 다시 재지는 않았다

## M1 — `QueryFullProcessImageNameW` 는 띄울 때의 경로를 그대로 돌려준다

| 단계 | Windows Server 2022 | Windows Server 2025 |
|---|---|---|
| ① 사용자 폴더 `…\x\app.exe` 를 띄운 직후 | `…\x\app.exe` | `…\x\app.exe` |
| ② 실행 중인 파일이 든 폴더 `x` 의 이름 바꾸기 | **된다** | **된다** |
| ② 뒤(자리에 `x` 가 없음)에 돌려주는 값 | **그대로 `…\x\app.exe`** (그 경로는 열리지 않음) | 같음 |
| ③ 같은 자리에 다른 폴더를 가리키는 연결(junction) `x` 만들기 | 된다 | 된다 |
| ③ 뒤에 돌려주는 값 | **그대로 `…\x\app.exe`** | 같음 |
| 그 값을 이름으로 다시 열어 풀면(`final_path`) | **바꿔 둔 파일 `…\target\app.exe`** | 같음 |
| 원시 경로(`PROCESS_NAME_NATIVE`)도 | 띄울 때의 값 그대로 | 같음 |

- **C1 은 성립한다.** 지금의 `verify_server` 는 "프로세스가 돌려준 글자열을 이름으로 다시 열어 푼 값"을 등록된 Exe 와 비교하므로, 가짜 프로세스가 자기 폴더를 진짜 설치 폴더로 가는 연결로 바꿔 두면 통과한다. 프로세스에 끼어들 필요가 없다.
- 돌려주는 글자열은 **띄운 쪽이 적은 모양 그대로**다. 러너의 임시 폴더가 `C:\Users\RUNNER~1\…` 이라 ①부터 짧은 이름이 섞여 나왔다.

### 곁가지 — 짧은 이름으로 띄운 프로세스

| | Windows Server 2022 | Windows Server 2025 |
|---|---|---|
| C: 의 짧은 이름 만들기 | 켜짐 | 켜짐 |
| `C:\PROGRA~1\PowerShell\7\pwsh.exe` 로 띄웠을 때 돌려주는 값 | `C:\PROGRA~1\PowerShell\7\pwsh.exe` | 같음 |

- 그래서 "풀기 전의 값이 `C:\Program Files\` 로 시작해야 한다"를 **글자 그대로** 넣으면, 짧은 이름으로 띄운 정상 프로그램이 막힌다(제미나이의 이 지적은 맞다).

## M2 — `GetNamedPipeServerProcessId` 는 파이프를 만든 프로세스의 PID 를 돌려준다(끝난 뒤에도)

순서: A 가 파이프를 만들고 서버 핸들을 물려받는 자식 B 를 띄운 뒤 끝난다. 파이프는 B 가 쥐고 있어 살아 있다. 클라이언트가 붙어 서버 PID 를 묻는다.

| | Windows Server 2022 | Windows Server 2025 |
|---|---|---|
| 돌려준 PID | **A (끝난 프로세스)** | **A (끝난 프로세스)** |
| 그 PID 로 실행 파일을 물으면 | 실패(os error 31) | 실패(os error 31) |

- 지금 코드에서는 이때 앱형이면 "상대를 확인하지 못함"으로 **거부**된다(실행 파일을 알아내지 못하므로).
- 그러나 **그 PID 를 다른 프로세스가 다시 받으면, 섀시는 그 프로세스의 실행 파일을 본다.** 공격자가 진짜 실행 파일을 되풀이해 띄워 A 의 PID 를 다시 받게 하는 데 성공하면 경로 대조를 통과한다. PID 를 실제로 다시 받게 만드는 것까지는 재지 않았다.
- 이 틈은 `GetNamedPipeServerProcessId` 를 쓰는 한 섀시 쪽에서 닫을 방법을 찾지 못했다(파이프를 지금 쥐고 있는 프로세스를 클라이언트가 알아내는 API 를 알지 못한다).

## 뜻하는 것

답변반영 0장의 결론을 측정이 뒷받침한다: **앱형 모듈의 서버 확인은 같은 사용자 권한의 공격자에 대한 보증이 아니다.** M1 의 틈은 좁힐 수 있고(아래), M2 의 틈은 남는다.

## C1 을 고친다면 (제안 — 기획자가 정한다)

- **(가) 풀기 전의 값도 관리자 폴더 아래여야 통과.** 프로세스가 돌려준 글자열(풀기 전)이 Program Files 폴더 아래여야 하고, 그것을 푼 값이 등록된 Exe 와 같아야 한다. Program Files 아래의 폴더는 일반 권한으로 이름을 바꾸거나 연결로 바꿀 수 없으므로 M1 의 순서가 막힌다. 짧은 이름으로 띄운 정상 프로그램을 막지 않도록, 관리자 폴더 목록에 **Program Files 의 짧은 이름 모양(`C:\PROGRA~1` 등, 운영체제에 물은 값)** 을 함께 둔다. 폴더 아래 마디의 모양은 따지지 않는다(그 아래는 모두 관리자만 고칠 수 있다).
- **(나) 고치지 않고 8.3 에 한계로만 적는다.** M2 가 남는 이상 서버 확인은 어차피 보증이 아니라는 이유.
- 권고는 (가): 고치는 양이 작고(비교 한 번), "끼어들지 않고도 되는" 가장 쉬운 길 하나를 막는다. 다만 (가)를 넣어도 M2 와 "진짜 실행 파일에 끼어들기"는 남는다는 것을 화면·문서에서 숨기지 않는다.
